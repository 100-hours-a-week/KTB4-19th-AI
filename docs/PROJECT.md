# zipsAI (집사이) 프로젝트 배경

이 문서는 코드가 아직 없는 이 저장소에서 작업할 때 "왜 이걸 만드는지"를 빠르게 파악하기 위한 배경 문서다. 아키텍처/코딩 규칙은 [CLAUDE.md](../CLAUDE.md)와 [CONVENTIONS.md](CONVENTIONS.md)를 따르고, 이 문서는 그 규칙들이 왜 그렇게 정해졌는지의 맥락을 제공한다.

## 왜 만드는가

원룸·고시원 같은 소형 주거 시설은 별도의 관리 시스템 없이 운영되는 경우가 많다. 민원과 시설 관리 정보가 카카오톡/전화/문자/수기장부/엑셀에 흩어져 있어 관리인이 전부 기억·정리해야 하고, 그 결과 민원 누락·처리 지연·반복 민원 파악 실패가 발생한다. 세입자 입장에서도 매번 집주인에게 직접 말하고 독촉해야 하는 감정적 피로가 있다.

zipsAI는 **집주인에게는 민원을 한 곳에 모아 보여주고, 세입자에게는 시간·감정 부담 없이 민원을 등록할 수 있게 하는** AI 기반 소형 주거시설 관리 플랫폼이다.

## 타겟 사용자

- **집주인/관리인**: 소형 주거 건물(원룸·다가구 등)을 직접 관리하는 소액 건물주. 위탁 관리 업체를 쓰기엔 수수료가 부담스러움.
- **세입자**: 소형 주거 시설 거주자. 집주인에게 직접 연락하는 것에 부담을 느낌.

### 페르소나

| | 집주인 (김철수, 58) | 세입자 (이지은, 26) |
|---|---|---|
| 상황 | 원룸·다가구 2개 동(24세대) 직접 운영 | 소형 원룸 거주 사회초년생 |
| 페인포인트 | 채널 파편화로 민원 누락/지연, 반복 민원 원인 파악 어려움, 적정 임대료 산정 난항 | 늦은 밤 문제 발생 시 연락 부담, 처리 상태 불투명, 단순 문의(쓰레기 배출일 등)도 매번 눈치 |
| 니즈 | 통합 대시보드, AI 기반 유형/긴급도/우선순위 정리, 시세 기반 임대료 제안 | 사진+설명만으로 접수 가능한 창구, 실시간 처리 상태 확인, RAG 챗봇 |

## 서비스 개념

세입자가 "화장실 천장에서 물이 떨어진다"와 사진을 올리면, AI가 뒤에서 민원을 분류·긴급도 판단·유사 민원 검색·정리해서 관리자에게 보기 쉽게 보여준다.

**기존 방식**: 세입자 연락 → 관리인 확인 → 관리인이 기억/기록 → 처리 (매번 처리 후 정보 소실)
**zipsAI**: 민원 접수 → AI 분석 → 관련 기록 연결 → 관리자 업무 정리 → 처리 이력 축적 (데이터가 쌓여 다음 관리에 재사용됨)

## 핵심 기능

- **AI 민원 관리**: 자동 분류, 요약, 긴급도 판단, 처리 우선순위 추천
- **사진 기반 시설 분석**: 누수·곰팡이·파손·고장 등을 사진+설명으로 VLM이 분석
- **유사 민원 통합**: 여러 호실의 서로 다른 표현("물이 약하다"/"수압이 이상하다")을 같은 원인(급수 문제)으로 묶어냄
- **반복 민원 발견**: 특정 호실/층/시설의 과거 기록을 연결해 반복 패턴 탐지
- **관리 대시보드**: 긴급 민원 / 미처리 민원 / 처리 중 작업 / 반복 시설 문제 / 점검 일정을 한 화면에
- **반복 문의 자동 응답**: 쓰레기 배출, Wi-Fi, 주차, 택배, 공용시설 이용법 등을 관리자가 업로드한 건물별 문서 기반으로 자동 답변 (RAG)

## AI 기능 (이 저장소가 담당하는 영역)

| 기능 | 방식 |
|---|---|
| 주거 문제 사진 분석 (문제 유형/증상/긴급도) | 멀티모달 LLM(VLM) |
| 건물별 공지·규칙·과거 민원 기반 답변, 반복 민원/이상 징후 탐지 | RAG |
| 사진 분석 결과 + 입주민 추가 응답 기반 확인사항 질문·조치 방향 생성 | LangGraph 기반 Agentic 플로우 |

## 시스템 아키텍처 (위키 기준)

Frontend → Backend → AI 서비스 순으로 엄격히 분리되며, 프론트엔드는 항상 백엔드를 거쳐서만 통신한다.

- **Backend**: 인증, 민원 저장, 상태 변경, 관리자 승인 등 실제 서비스 상태(state)에 영향을 주는 모든 것을 담당.
- **AI 서비스**: 모델 추론, RAG, 민원 분석, 건물 문의 응답, 인사이트 생성을 독립적으로 수행. **분석 결과만 반환하며 직접 데이터를 쓰지 않는다** — 민원 등록/승인/비용 책임 판단 같은 critical operation은 항상 백엔드가 최종 결정. AI 장애가 서비스 데이터를 훼손하지 않도록 하기 위함.

AI 내부는 세 모듈로 나뉘며, 이는 [CLAUDE.md](../CLAUDE.md)의 `complaint/` / `knowledge/` / (향후) `insights/` 디렉터리와 대응한다:

1. **민원 분석 (complaint)**: 텍스트/이미지에서 민원 유형·위치·증상 추출
2. **건물 지식 검색 (knowledge)**: 문서 검색 + 근거 기반 답변
3. **AI 인사이트 (insights, 후속 기능)**: 과거 민원 데이터에서 반복 이슈 후보 생성. 실시간 대화와 자원 경합을 피하기 위해 매일 05:00 KST 배치로 별도 실행.

데이터 흐름: 사용자 메시지 → 백엔드가 컨텍스트 검증 → AI Agent가 intent 분류(민원/지식질의/명확화 질문) → 해당 모듈 처리 → AI는 분석 결과만 반환 → 백엔드가 검증 후 영속화.

### API 개요

상세 요청·응답 예시와 필드 정의의 기준은 팀 위키의 [AI 모델 API 설계](https://github.com/100-hours-a-week/KTB4-19th-wiki/wiki/%5BAI%5D-%EB%AA%A8%EB%8D%B8-API-%EC%84%A4%EA%B3%84)다. 민원 흐름에만 쓰이는 상태는 `complaint_state`/`next_complaint_state`로 구분한다.

- `POST /api/v3/ai/converse` — 실시간 질의·민원·명확화 대화 진입점이다. Backend가 건물·세입자 컨텍스트, 새 메시지, 대화 이력, 진행 중인 민원 초안을 전달하고 AI는 최상위 `trace_id`와 `route`, `requested_action`, `next_complaint_state`, `reply`, feature별 `result`, `meta`를 반환한다.
- `POST /api/v3/ai/insights/generate` — 인사이트 배치 워커가 매일 05:00 KST에 호출한다. 최근 7일과 직전 7일 민원 데이터를 비교해 관리자가 검증할 반복 이슈 후보를 반환한다.
- `GET /health` — 로드밸런서·모니터링이 AI 서비스, Vector DB, 모델의 준비 상태와 prompt version을 확인한다.

`current_route`는 직전 응답을 무조건 복사하는 값이 아니라, **아직 종료되지 않은 대화 흐름이 있을 때만** Backend가 전달한다. 민원 내부 진행 상태는 `complaint_state`로 별도 전달하며, `current_route`가 `complaint`가 아니면 `complaint_state`와 `next_complaint_state`는 `null`이다. AI는 분석 결과만 반환하며 민원 저장, 상태 변경, 알림 발송 같은 쓰기 동작을 하지 않는다.

오류는 `trace_id`를 포함한 공통 형식으로 반환한다. 표준 상태 코드는 `400`(필수 입력 누락), `422`(계약 검증 실패), `429`(모델 rate limit), `500`(AI 내부 오류), `502`(모델·검색 upstream 오류), `503`(의존성 미준비), `504`(모델·검색 timeout)다.

## 초기 MVP 범위

- 관리자의 건물 등록 / 세입자 초대
- 세입자 민원 등록
- AI 분류 및 요약, 사진 분석, 유사 민원 탐지
- 관리자 대시보드, 처리 상태 관리

MVP 이후: 반복 문제 분석 → 이상 징후 발견 → 예방 점검 추천 (`insights/`).
