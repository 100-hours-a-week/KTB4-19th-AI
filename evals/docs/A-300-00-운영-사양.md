# A-300-00 운영 평가 사양

AI 서비스(`ai-api`) 전체 — 인덱싱·질의·민원의 동작·속도·실패만 본다.   
품질(답이 맞았나)은 A-100/A-200이 담당 — **운영 지표로 품질을 판정하지 않는다.** 답이 틀려도 `outcome=ok`로 기록된다.   
운영 평가에서는 LLM Judge 대상 지표는 없다 — I·Q·S 전부 코드 집계다.

## 0. 측정 단위와 방법

**무엇을 한 열로 기록하나** — 배포 하나가 운영에 있던 기간 전체가 한 열이다. 기간은 main에 머지된 시각이 아닌, 운영 배포 완료 시각(AI CD 실행이 끝난 시각)에서 다음 배포 완료 직전까지다. 버전 이름은 `A-000-00` §3 참고.

**무엇을 읽나** — CloudWatch Logs Insights로 그 기간의 실사용 로그(`/zipsai/prod/ai-api`)만 읽는다. 채팅 API로 새 질문을 보내지 않는다.

**언제·어떻게 재나 (수동)** — 새 배포가 나가면 직전 배포의 기간이 닫히므로, 그때 한 번 집계한다.

1. 기간 확인 — 성공한 AI CD 실행만 경계로 쓴다. 실행 목록은 `gh run list --workflow ai-cd.yml --repo 100-hours-a-week/KTB4-19th-AI --status completed --json databaseId,updatedAt,headSha,conclusion`으로 보고, `conclusion=success`인 실행의 완료 시각(`updatedAt`)을 사용한다. `headSha`는 workflow 실행에 사용된 저장소 SHA이지 배포 이미지 SHA라는 보장이 없다.
   ```sh
   aws ssm get-parameter-history --name /zipsai/prod/deploy/ai-api/current-sha --query 'Parameters[].{Time:LastModifiedDate,SHA:Value}' --output table
   aws ssm get-parameter-history --name /zipsai/prod/deploy/embedding/current-sha --query 'Parameters[].{Time:LastModifiedDate,SHA:Value}' --output table
   ```
   두 명령에서 성공 배포 시점에 기록된 각 서비스 SHA를 확인한다. 배포 입력은 서비스별로 생략될 수 있으므로 workflow 입력만으로 실제 실행 중인 두 SHA를 대신하지 않는다.
2. Logs Insights에서 로그 그룹 `/zipsai/prod/ai-api`, 시간 범위를 1번 기간으로 잡는다.
3. §8 쿼리를 §6 판정 순서대로 돌린다(트래픽 성격 → 유실 → 실패 → 지연).
4. `A-300-01`에 열을 추가하고 버전·SHA·기간, 값마다 n, `✗`·`판정 보류`·`⚠테스트`를 적는다.

**보관 기한** — 문서상 전제인 30일 보관은 각 로그가 생성된 시점부터 계산한다. 배포 기간이 30일보다 길면 기간 종료까지 기다릴 경우 앞부분 로그가 먼저 만료될 수 있으므로, 보관 전에 일별 또는 중간 집계를 저장한다. 만료된 원본을 복원할 수 없으면 해당 기간 전체값으로 기록하지 않는다. 현재 로그 그룹의 실제 보관 설정은 확인되지 않았다.

**매일은 점검만 한다** — 알람 메일(단계 실패·60초 초과·색인 유실, §7)을 확인하고, 이상하면 그날 쿼리를 열어 본다. 점수표에는 배포 단위로만 적는다.

## 1. 로그 구조

### 1-1. 로그 3층

```
① 단계 로그   stage_done        단계마다 1줄 — 어디서 얼마나 걸렸나
② 요약 로그   index_done·job_done·request_done   작업/요청마다 1줄 — 전체 결과와 실패 단계
③ 알람        메트릭 필터 → 알람 → SNS → 이메일(자동 감시)
```

①만 있으면 요청 하나의 전체 시간을 알려고 여러 줄을 이어 붙여야 한다. ②만 있으면 어디서 느렸는지 모른다. ③은 사람이 안 볼 때 대신 본다.

### 1-2. 로그 이벤트 종류


| `event`            | 언제 남나                 | 묶는 키                   |
| ------------------ | --------------------- | ---------------------- |
| `job_accepted`     | 색인 요청을 받자마자(202 응답 전) | `job_id`               |
| `stage_done`       | 단계 하나가 끝날 때마다         | `job_id` 또는 `trace_id` |
| `index_done`       | 문서 한 건의 색인이 끝날 때      | `job_id`               |
| `job_done`         | 색인 요청 하나가 끝날 때(정리 포함) | `job_id`               |
| `request_done`     | 질의/민원 요청 하나가 끝날 때     | `turn_id`              |
| `complaint_turn`   | 민원 대화 한 턴이 끝날 때         | `turn_id`              |
| `fallback`         | 근거를 못 찾아 회피할 때        | `turn_id`              |
| `agent_error`      | 의존성·LLM 실패로 에러 응답할 때  | `turn_id`              |
| `validation_error` | 요청 검증 실패(400·422)     | —                      |
| `unhandled_error`  | 예상 못 한 500            | —                      |


**`index_done`과 `job_done`이 따로인 이유** — 한 요청에 "문서 색인"과 "정리(없어진 문서 삭제)"가 함께 올 수 있다. 둘을 한 이벤트로 묶으면 `job_done`이 두 번 나와 I3의 유실 탐지(`accepted`−`done`)가 어긋난다.

### 1-3. 단계(`stage`) — 세 경로

**인덱싱 9단계** — `job_accepted → setup → download → parse → mask → clean → chunk → embed → upsert → reconcile → job_done`

**질의 6단계** — `intent → encode → gate → hybrid → context → generate`. 게이트 미달이면 `hybrid`·`context`·`generate`는 전부 생략되고 `fallback`으로 간다.

**민원 2단계** — `text_extraction`(LLM) → `image_analysis`(VLM, 이미지가 없으면 `skipped`). 단계 이름은 baseline `aa18cc0` 기준이고, `feat/95` 작업본 코드는 `text_extraction` 대신 `text_interpretation`을 쓴다(`complaint/node.py`)

### 1-4. 실패 표시

`stage_done`의 `outcome`은 `ok`·`fail`·`skipped` 셋이다. `fail`에는 `error_type`·`error`·`traceback`이 붙는다. `skipped`는 앞 단계에 막혀 아예 안 돈 것이다(게이트 차단 시 `hybrid`·`context`·`generate`, 이미지가 없을 때 `image_analysis` 등).


| 예외(`error_type`)                                                            | 어느 단계                                       | 응답                      |
| --------------------------------------------------------------------------- | ------------------------------------------- | ----------------------- |
| `DocumentFetchError`·`PdfParseError`·`EmptyDocumentError`                   | `download`·`parse`·`upsert`                 | 색인 실패(응답 없음, 202 이미 나감) |
| `EmbeddingError`                                                            | `embed`·`encode`                            | 색인 실패 / 질의 **503**      |
| `VectorStoreError`                                                          | `gate`·`hybrid`·`upsert`                    | 질의 **503**              |
| `IntentClassificationError`·`ComplaintExtractionError` | `intent`·`text_interpretation` | **502** |
| `LlmRateLimitedError`                                                       | `intent`·`generate`                         | **429**                 |
| `LlmTimeoutError`                                                           | 같음                                          | **504**                 |
| `LlmUpstreamError`                                                          | 같음                                          | **502**                 |
| `LlmUnavailableError`                                                       | 같음                                          | **503**                 |

사진이 포함된 요청에서 `ImageAnalysisError`는 `intent` 단계 안에서 처리해 텍스트만으로 분류를 이어가거나 `clarify`로 보낸다. 민원 응답에는 사진 분석 실패 안내가 붙는다. 이 복구 경로는 `ImageAnalysisError` 자체를 API의 502 응답으로 반환하지 않는다. 위 표의 502는 전파된 `IntentClassificationError`·`ComplaintExtractionError`에 해당한다.


### 1-5. `cold`가 뭔가

프로세스 기동 후 **첫 색인 작업 한 번만** `cold=1`이다. 첫 작업은 docling이 OCR·레이아웃 모델을 디스크에서 올려서 `parse`가 warm 대비 최대 8.6배 느려진다(실측 23,663ms vs 2,739~8,291ms). `cold`를 안 가르면 "파싱이 평균 9.5초"라는 숫자가 나오는데, 실제로는 모델 로딩 1회와 파싱 여러 회를 섞은 값이라 의미가 없다.

## 5. 측정 해상도와 판정 규칙


| 규칙                   | 내용                                                         |
| -------------------- | ---------------------------------------------------------- |
| n을 먼저 적는다            | 비율·백분위를 판정하기 전에 그 창의 건수 n을 적는다                             |
| n &lt; 100이면 비율을 버린다 | 건수로 판정하고 p99는 계산하지 않는다                                     |
| n &lt; 10이면 값만 나열한다  | 평균·p95를 쓰지 않는다                                             |
| 실패는 언제나 건수           | 실패·유실·에러는 비율로 보지 않는다 — 1건이 곧 사고다                           |
| `cold`를 갈라서 본다       | `download`·`parse`·`embed`는 `cold=1`과 `cold=0`을 절대 합치지 않는다 |
| 2회 연속에 조치            | 1회 이탈은 기록만. **예외** — 실패·유실·에러는 1건에 즉시                      |


## 6. 판정 순서

```
S0 트래픽 성격 확인(top_score 고유값·시각 분포 — 테스트 반복이면 Q5·Q6 판정 보류)
  ↓
S1 로그가 오는가           실패 → 아래 전부 판정 불가
  ↓
I3·Q9 유실·증발            실패 → 남은 로그는 성공 편향
  ↓
S7 건물별 색인 커버리지     불일치 → Q5·Q6은 "문서 없는 건물에 질의한 결과"일 수 있다
  ↓
I2·Q4 실패·에러            실패 → 지연 지표는 성공 케이스만의 값
  ↓
I1·Q1·Q3 지연
  ↓
S2~S6 서비스 전반
```

| 알람                               | 조건                                | 지키는 지표 |
| -------------------------------- | --------------------------------- | ------ |
| `zipsai-ai-stage-failed`         | `StageFailed` Sum≥1 / 300초        | I2     |

**지표별 감시 상태** — 알람 있음: I2·I3·Q2. 수동 쿼리만: I1·I4~~I10·Q1·Q3·Q5~~Q8·S1~S5. 사각지대(로그·메트릭 둘 다 없음): S6, 아래 §9 전부. **가장 큰 구멍은 지연이다** — 실패·유실은 알람이 잡지만 "실패는 안 했는데 느려진" 상태는 아무도 안 알려준다. Q2가 60초 초과만 잡아서, 20초가 40초로 늘어도 조용하다.

## 8. Logs Insights 쿼리

로그 그룹 `/zipsai/prod/ai-api`. 프로필 `zipsai-qdrant-reader`, 리전 `ap-northeast-2`. **별칭에 한글을 쓰면 `MalformedQueryException`** — `as n`만 쓴다.

### Q13 Langfuse 토큰 집계

CloudWatch에는 토큰 필드가 없다. Langfuse에서 해당 시간창·`run_id`·모델·generation 이름을 맞춘 뒤 `usage_details`에서 `prompt_tokens`·`completion_tokens`를 export하거나 합산한다. `total_tokens = prompt_tokens + completion_tokens`, `estimated_cost = prompt_tokens×입력단가 + completion_tokens×출력단가`. 단가가 없으면 비용은 `—`로 둔다. 질문·답 본문은 집계 문서에 복사하지 않는다.
