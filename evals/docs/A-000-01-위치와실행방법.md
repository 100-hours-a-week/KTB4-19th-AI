# A-000-01 벤치마크 위치와 실행 방법

`A-000-00-문서지도.md` §2에서 가리키는 상세 문서. "시험지가 어디 있고, 어떤 순서로 돌려야 안 막히는지"만 다룬다. 

## 1. 한눈에 — 돌리기 전에 알아야 할 3가지

1. **전부 로컬이다.** 운영 서비스(`ai-api`)에는 테스트 질문을 보내지 않는다.
2. **작업 폴더는** `KTB4-19th-AI/ai`**.** 저장소 루트에서 `../evals`를 치면 파일을 못 찾는다.
3. **순서가 있다.** Qdrant·임베딩이 떠 있어야 하고, 검색 채점(T1)이 먼저 돌아 컬렉션을 채워야 답변 채점(T2)이 그 위에서 동작한다.

## 2. 시험지 총량

평가에 쓰는 시험지는 세 덩어리다.

- **질의 문항 302개** — 건물 문서를 보고 답해야 하는 질문
- **민원 문항 160개** — 고장·불편 접수 대화 38개 + 사진 120개 + 사진 실패 파일 2개
- **색인 원본 문서 51건** — 질의 문항이 답을 찾아보는 건물 문서이고, 평가 전에 먼저 검색 DB에 넣어 둔다.

문항 수는 이 표를 기준으로 한다. §3 지표별 표는 여기 묶음 이름으로 가리킨다. 파일 경로는 `evals/synthetic/2-reproduce/` 기준이다.

### 문항 구성 — 왜 이렇게 나뉘어 있나

**질의 302문항 — 유형별로 재는 것**

| 유형 | 개수 | 어떤 질문인가 | 재는 지표 |
| --- | --- | --- | --- |
| 답있음 · 건물 고유 | 97 | 건물마다 답이 다른 질문(주차·관리비 등) | R1(격리), R2·R4~R7, G1·G2·G5·G6·G7, C1 |
| 답있음 · 공통 | 38 | 여러 건물 문서에 같은 내용이 적힌 질문(쓰레기 요일 등) | R2·R4~R7, G1·G2·G5·G6·G7, C1 (R1 제외) |
| 답없음 | 100 | 건물 문서에 답이 없어 "모른다"고 해야 하는 질문 | R3(게이트 차단), G1·G5·G6·G7, C1 |
| 부분 답변 | 15 | 일부만 문서에 있는 질문 | G3, C1 |
| 공격 | 20 | 원래 규칙을 무시하라는 지시를 숨긴 질문 | G4, C1 |
| 후속 질문 | 12 | "그거 어디 둬요?"처럼 앞 대화를 알아야 하는 2턴 질문 | C3, C1 |
| 되묻기 | 20 | "네"처럼 애매해서 되물어야 하는 질문 | C2 |
| **합계** | **302** | | |

- 답있음과 답없음을 둘 다 둔 것은 게이트를 양쪽에서 재기 위해서다. 답 있는 질문은 통과시키는지(R2), 답 없는 질문은 막는지(R3). 답없음은 건물마다 10개씩이다(10개 건물 × 10).
- 답있음 135는 건물 고유 97 + 공통 38이다. 문서는 모두 건물별로 따로 있고, 검색이 다른 건물의 문서를 답변에 쓰지 않는지(격리, R1)를 확인한다. 이 판단은 건물마다 답이 다른 건물 고유 97문항으로만 한다. 쓰레기 배출 요일처럼 여러 건물의 문서에 같은 내용이 적힌 공통 38문항은 다른 건물 문서를 써도 답이 같아서 판별에 쓸 수 없기 때문이다.
- G1·G2·G5·G6·G7은 답있음·답없음 중 대표 100문항(답있음 60 + 답없음 40)에 답을 쓰게 해서 잰다. C1은 되묻기를 뺀 282문항이 모두 건물 문의(knowledge)로 가는지 본다. C2는 되묻기 20 + 민원 글 20으로 잰다.
- 문서 51건은 색인 파이프라인의 분기(스캔본, 개인정보 탐지, 반복 머리말, 표, 개정판 교체 등)를 모두 거치도록 만든 합성 문서이고, 정답셋과 한 묶음이다. 개인정보 탐지를 위해 가짜 개인정보를 일부러 넣었다.

**민원 글 38문항** — 한 턴 완결 10 · 재질문(위치만 빠짐 4, 증상만 빠짐 4) 8 · 2턴 완결 6 · 택소노미 경계 10 · 환각 유도 4. 환각 유도는 위치를 말하지 않은 민원이다. 모델이 위치를 지어내지 않고 되물어야 정답이다(M8).

**사진 122장**은 "이상 / 정상" × "글자 있음 / 없음" 2×2로 30장씩 만들었다.

| 코드 | 사진 | 읽어야 할 글자 | 요약에 꼭 들어갈 말(예) |
| --- | --- | --- | --- |
| AO | 이상 + 글자 있음 | 있음 | 보일러·세탁기·도어락 (에러코드 `E04`, `E01 41°C` 등) |
| AN | 이상 + 글자 없음 | 없음 | 곰팡이·누수·균열·얼룩·싱크대 |
| NO | 정상 + 글자 있음 | 있음 | 세탁기·엘리베이터·에어컨 (`55°C`, `5F`, `24°C` 등) |
| NN | 정상 + 글자 없음 | 없음 | 거실·세면대·소파·침대 |

- 120장 모두 사진에 없는 위험 단어(바퀴벌레·불꽃 등)를 요약에 쓰면 안 되는 말로 갖고 있다. 없는 것을 지어내지 않는지 보는 장치다.
- 글자 없는 60장(AN·NN)의 정답은 "읽을 글자 없음"이다. M4는 글자가 있는 사진을 정확히 읽는지와 글자 없는 사진에서 아무것도 지어 읽지 않는지를 함께 본다.
- **사진 실패 2개**는 깨진 jpeg와 확장자만 jpeg인 파일이다(M6).

### 색인 원본 51건 — 문항이 아니라 질의가 찾아보는 문서

- **무엇인가** — `evals/synthetic/1-dataset/build/`에 있는 건물 문서다(PDF 49 · PNG 1 · JPG 1).
- **왜 필요한가** — 질의 문항은 이 문서들을 검색해서 답을 찾는다. 그래서 평가 전에 이 51건을 검색 DB(Qdrant)에 먼저 넣어(색인) 둬야 한다. T1을 돌리면 이 작업이 같이 실행된다(§5).
- **어디에 쓰나** — R1~R7은 이 문서에서 정답을 찾는지 보고, K1은 파싱한 텍스트가 검색 DB에 들어가는 동안 뜻이 보존됐는지 점검한다. K1은 T1이 넣어 둔 결과를 읽을 뿐 질문은 따로 보내지 않는다.

### 그 밖의 안내

- 민원 사진 120장은 저장소의 `evals/synthetic/2-reproduce/complaints/photos/`에 있다. `run_m2.py`는 이 저장소 상대 경로를 기본값으로 쓰며, 다른 폴더면 `--photos-dir`로 바꾼다.
- 운영(I·Q·S)은 시험지가 없다. 실사용 트래픽의 CloudWatch 로그가 시험지를 대신한다(`A-300-00` 참조).

## 3. 지표별 — 뭘 보고, 어느 문항을 쓰나

지표별 계산식·목표·채점 방식은 `A-100-00`(질의)·`A-200-00`(민원)이 정본이다 — 여기는 "이 지표가 뭘 보고, §2 시험지 총량 중 어느 문항을 쓰는지"만 한눈에 보는 표다. 질의 17개 + 색인 1개(K1)이고, 민원 9개는 별도다. 운영(I·Q·S)은 벤치마크가 없어 제외한다.

## 5. 실행 순서

```bash
# 1) Qdrant (저장소 루트에서)
docker compose up -d qdrant

# 2) 임베딩 — 컨테이너가 이미 있으면 docker run이 실패한다. 그땐 둘째 줄만 쓴다.
docker run -d --name t1-embedding -p 127.0.0.1:8001:8000 zipsai-embedding:cpu
docker start t1-embedding

# 3) 임베딩이 응답하는지 먼저 확인 — 모델이 다 올라오기 전엔 health가 안 된다
curl -s http://127.0.0.1:8001/health
```

위 셋이 끝난 뒤 아래 명령은 저장소의 `ai/` 디렉터리에서 실행한다.

```bash
cd ai
RUN_ID="$(date +%Y%m%d-%H%M%S)-$(git rev-parse --short HEAD)"
RESULTS="../evals/results/${RUN_ID}"
mkdir -p "$RESULTS"

# 4) 검색 채점(T1) — R1~R7. 문서 51건을 documents_eval에 재색인한다
uv run python ../evals/query/run_t1.py --embedding http://127.0.0.1:8001 --out "$RESULTS/run_t1.json"

# 5) 색인 채점 — K1. T1이 색인한 결과를 읽는다. LLM_JUDGE_MODEL이 없으면 돌지 않는다
uv run python ../evals/query/run_k1.py --qdrant http://127.0.0.1:6333 | tee "$RESULTS/run_k1.txt"

# 6) 답변 채점(T2) — G1·G2·G5·G6. T1이 만든 컬렉션 위에서 돈다. G1은 LLM_JUDGE_MODEL이 있어야 판정한다
uv run python ../evals/query/run_t2.py --embedding http://127.0.0.1:8001 --out "$RESULTS/run_t2.json"

# 6-1) 답변 충실도 채점 — G7. T2 결과(근거 본문 포함)를 읽어 judge만 돌린다. 답변을 다시 만들지 않는다
uv run python ../evals/query/run_g7.py --from "$RESULTS/run_t2.json" --out "$RESULTS/run_g7.json" | tee "$RESULTS/run_g7.txt"

# 7) 길 고르기 채점(T3) — C1. 검색·답변 없이 라우팅만 본다
uv run python ../evals/query/run_t3.py --check
uv run python ../evals/query/run_t3.py | tee "$RESULTS/run_t3.txt"

# 8) 확장 답변 채점 — G3·G4·C3. T1 컬렉션을 그대로 쓴다
uv run python ../evals/query/run_ext_answer.py --embedding http://127.0.0.1:8001 | tee "$RESULTS/run_ext_answer.txt"

# 9) 확장 길 고르기 채점 — C2. 검색 없이 길만 본다
uv run python ../evals/query/run_ext_route.py | tee "$RESULTS/run_ext_route.txt"

# 10) 민원 글 채점 — M1·M2·M7·M8·M9
uv run python ../evals/complaint/run_m1.py | tee "$RESULTS/run_m1.txt"

# 11) 민원 사진 채점 — M4·M5·M6
uv run python ../evals/complaint/run_m2.py | tee "$RESULTS/run_m2.txt"
```

T1·T2는 `--out`을 줘야 JSON이 남고, 나머지 평가 스크립트는 표준 출력에만 점수를 쓰므로 `tee`로 파일에 남긴다. 원시 결과는 `evals/results/<실행ID>/`에 보관한다. 확정 점수와 실행 해석은 `A-100-01`·`A-200-01`에 기록한다.

**이미 넣어 둔 컬렉션으로 검색만 다시 채점**할 때는 4번 줄에 `--score-only`를 붙인다 — 51건 재색인을 건너뛴다.

## 6. 자주 걸리는 함정 3가지


| 증상                            | 원인                                 | 대처                                                    |
| ----------------------------- | ---------------------------------- | ----------------------------------------------------- |
| `docker run`이 "이름이 이미 있다"며 실패 | `t1-embedding` 컨테이너가 이전 실행에서 남아 있음 | 새로 만들지 말고 `docker start t1-embedding`                 |
| 파이썬 스크립트가 연결 오류로 바로 죽음        | 임베딩 모델이 아직 메모리에 안 올라옴              | `curl http://127.0.0.1:8001/health`가 응답할 때까지 기다린 뒤 실행 |
| `FileNotFoundError`류 오류       | 저장소 루트에서 명령을 침(`../evals`가 안 맞음)   | 반드시 `KTB4-19th-AI/ai` 안에서 실행                          |
