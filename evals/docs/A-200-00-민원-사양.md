# A-200-00 민원 평가 사양

`intent_route=complaint` 경로의 정의서. 민원은 **정보를 받아내는 대화**다 — 답이 맞았나가 아니라 "접수할 수 있을 만큼 받았나"를 본다.

## 1. 민원 기능의 기본 규칙 — 지표가 기대는 전제

민원 지표는 아래 규칙을 기준으로 채점한다. 규칙이 코드에서 바뀌면 지표 해석도 같이 바뀐다.

| 규칙 | 값 | 코드 위치 | 관련 지표 |
| --- | --- | --- | --- |
| 필수 필드 | `location`·`symptom` 2개 | `complaint/node.py` `_REQUIRED_FIELDS` | M1·M8 |
| 민원 유형(택소노미) | 10종(`water_supply`·`drain`·`leak`·`heating`·`electricity`·`mold`·`pest`·`facility`·`noise`·`other`) | `contracts/converse.py` | M2·M9 |
| 실제 쓰이는 상태 | `collecting`(정보를 모으는 중)과 `null` 둘뿐 | `complaint/node.py` `ComplaintState.COLLECTING` | — |
| 한 턴에 되묻는 개수 | 빠진 필드 중 1개(`missing_fields[0]`) | `complaint/node.py` | M3 |

## 2. 지표 9개

| ID | 지표 | 계산 절차 | 목표 | 채점 방식 | 이게 나빠지면 | 미달 시 조치 |
| --- | --- | --- | --- | --- | --- | --- |
| M1 | 필수필드 추출 정확도 | `location`·`symptom` 필드별 완전일치(앞뒤 공백 제거). 분모는 38문항 × 2필드 = 76칸 — 두 필드를 다 맞힌 민원 비율이 아니다 | ≥0.90 | 코드 | **접수가 안 된다.** 필수 2개가 없으면 대화가 안 끝남 | `complaint/prompts.py`의 추출 예시 보강 |
| M2 | 택소노미 분류 정확도 | 10종 중 정답 라벨 일치 | ≥0.80 | 코드 | 관리자가 엉뚱한 담당에게 보낸다 | 택소노미 10종의 경계 예시를 프롬프트에 추가 |
| M3 | LLM 재질문 채택률 | `reply_source=llm` ÷ 재질문 턴 | ≥0.50 | 코드 — **운영 로그로만** 집계(로컬 38문항엔 이 비율이 없음) | 낮으면 고정 문구만 나가 대화가 기계적으로 들림 | LLM 재질문이 정확히 한 필드만 묻게 프롬프트 조정 |
| M4 | VLM OCR 정확도 | `ocr_text` 완전일치 | ≥0.80 | 코드 | 보일러 에러코드 `E04`를 `EO4`로 읽으면 쓸 수 없음 | VLM 프롬프트에 "코드는 글자 그대로" 규칙 추가 |
| M5 | VLM 요약 적합성 | `must_include` 전부 있고 `must_not_include` 없음 | ≥0.80 | **규칙 기반**(`summary_ok` — 필수어 포함·금지어 배제). LLM Judge 설계는 `A-900-00` | 요약이 틀리면 관리자가 잘못된 상황을 봄 | VLM 요약 프롬프트 조정 |
| M6 | 사진 실패 고지율 | 분석 실패 시 고지 문구로 시작하는지 | =1.00 | 코드 — prefix match | 실패했는데 조용하면 사용자는 사진이 반영된 줄 안다 | `complaint/node.py:210` `_PHOTO_FAILED_PREFIX` 확인 |
| M7 | 추출 재시도율 | 재시도 발생 턴 수 ÷ 전체 추출 턴 수(턴 단위 중복 제거) | ≤0.05 | 코드 — `run_m1.py`가 로그를 캡처해 집계 | 재시도가 잦으면 프롬프트나 모델이 불안정 | 출력 스키마를 좁히거나 모델 교체 |
| M8 | 필드 환각 건수 | 기대값이 `null`인데 모델이 채운 건수 | 0건 | 코드 — exact/null 비교 | **위치를 지어내면 엉뚱한 곳을 고치러 간다.** 가장 큰 사고 | 1건이라도 재현한 뒤 프롬프트 강화 |
| M9 | `other` 도피율 | `issue_type=other` 비율 | ≤0.20 | 코드 | 전부 `other`면 분류가 사실상 없는 것 | `complaint/node.py:327`에서 빈 `issue_type`을 `other`로 채움 — 추출값을 봐야 함 |

**M7 보충** — M7은 추출이 한 번에 성공하지 못하고 다시 시도한 비율이다. 재시도 여부는 민원 노드의 구현에 따라 달라지므로, 노드를 바꿨을 때 추출이 안정적인지 보려고 둔다. `run_m1.py`는 노드가 남기는 재시도 로그를 세서 집계한다 — 노드가 로그 이벤트 이름을 바꾸면 러너도 맞춰야 하며, 맞지 않으면 재시도가 있어도 0으로 나온다.

## 3. 채점 방법 — 어떤 평가 스크립트가 어떤 지표를 내나

민원 지표는 평가 스크립트 두 개(`run_m1.py`,`run_m2.py`)가 낸다. 둘 다 모델에게 채점을 맡기지 않고 코드로 정답과 비교한다(`evals/complaint/score_m.py`). M3는 운영 로그(`complaint_turn.reply_source`)로만 잰다 — 로컬 문항에는 이 값이 없다.

| 평가 스크립트 | 넣는 것 | 내는 지표 | 정답과 비교하는 방법 | 결과 파일 |
| --- | --- | --- | --- | --- |
| 민원 글 채점 (`run_m1.py`) | 민원 글 38문항. 2턴 대화 6개가 있어 사용자 발화는 44턴 | M1·M2·M7·M8·M9 | 위치·증상·유형 값이 정답과 똑같은지(`same`), 재시도 로그 수 | `run_m1.txt` |
| 민원 사진 채점 (`run_m2.py`) | 사진 120장 + 실패 파일 2개 | M4·M5·M6 | 읽은 글자가 정답과 똑같은지(`ocr_same`), 요약에 꼭 들어갈 말이 있고 금지어가 없는지(`summary_ok`), 실패 문구로 시작하는지 | `run_m2.txt` |

**사진 120장의 구성 (실패 파일 2개는 제외)** — "이상 / 정상" × "글자 있음 / 없음" 2×2로 30장씩이다(코드 AO·AN·NO·NN, 자세한 표는 `A-000-01` §2). 글자 없는 60장(AN·NN)의 정답 `ocr_text`는 `null`이라, M4는 글자를 정확히 읽는지와 글자 없는 사진에서 아무것도 지어 읽지 않는지를 함께 본다. 120장 모두 사진에 없는 위험 단어(바퀴벌레·불꽃 등)를 `must_not_include`로 갖는다.

## 4. 판정 규칙

질의 채점표와 같은 규칙을 쓴다. 민원에만 해당하는 것만 적는다.

| 규칙 | 내용 |
| --- | --- |
| **지표마다 독립 판정한다** | 각 지표는 해당 평가 대상의 결과로 판정한다. 다른 지표의 목표 미달을 이유로 판정을 무효로 하지 않는다. 개별 지표의 합격을 민원 기능 전체의 합격으로 넓혀 읽지 않는다 |
| **M8은 1건에 즉시 조치** | 위치를 지어내면 사람이 엉뚱한 곳에 간다. 2회 연속을 기다리지 않는다 |
| **M6은 1.00이 목표** | 사진 실패 고지는 규칙이다. 미달은 버그다 |
| **표본이 작다** | 38문항에서 0.90은 약 ±10%p다. 5%p 격자로 임계값을 두고 10%p 미만 변화는 잡음으로 본다 |
