# 생성 이미지 후보 접수 현황

`image_candidates.jsonl`은 `/Users/daeunbaek/nuebaek/ktb/zipsai/data`의 생성 JPG를 `photos/candidates/`에 복사하고 SHA256을 기록한 **후보 목록**이다. 원본은 수정하지 않았다. `intended_group`은 생성 요청의 의도(AO=비정상·OCR, AN=비정상·무문자, NO=정상·OCR, NN=정상·무문자)일 뿐 실제 정답이 아니다. 전부 `review_status=pending`이며 검수 전에는 `photo_cases.jsonl`을 만들지 않는다.

사용자는 Grok으로 생성했다고 설명했다. 정확한 생성 모델 버전·설정·원본 프롬프트별 실행 기록은 아직 확보되지 않아 생성기 출처는 사용자 진술 수준으로 기록한다. 평가 대상 VLM과 생성기의 관계도 baseline 해석 전에 확인한다.

## 골든 셋 편입 순서

1. 각 사진을 열어 `visible_facts`, 실제 `gold_ocr`, 핵심 코드·수치, 판독 불가 영역, 사진 품질을 **픽셀 기준**으로 기록한다. 생성 프롬프트 문구를 정답으로 복사하지 않는다.
2. `reported_issue_type`과 사진에서 보이는 `visible_anomaly=true/false/unknown`을 따로 기록한다. AO/AN/NO/NN 폴더명으로 실제 상태를 강제하지 않는다.
3. 독립 검토자가 OCR 한 글자 차이와 정상/이상 경계를 확인한다. 미합의 사례는 `review_status=needs_adjudication`으로 남기고 확정 점수 분모에 넣지 않는다.
4. 승인된 사진만 `photo_cases.jsonl`의 실행 스키마로 옮긴다. 기존 필수 필드(`device`, `anomaly`, `gold_ocr`, `key_tokens`, `required_facts`, `forbidden`, `refs`, `tags`)에 후보의 `image_path`, `image_sha256`, `source_type`, `review_status="approved"`를 함께 기록한다. `anomaly`는 눈에 보이는 이상 여부(`true`/`false`/`"unknown"`)다. `unknown`은 보존하고 이상/정상 판정 지표의 분모에서만 제외한다. 실행 전 검사는 후보 경로의 승인 상태와 파일 해시를 확인한다. 같은 장면의 변형은 개발·최종 셋에 나누지 않는다. 생성 사진의 결과는 합성 조건 평가로 보고하고, 실사용 품질 판단에는 별도 실사진 holdout을 사용한다.

필드 정의와 분모는 [METRICS.md](METRICS.md)의 현재 평가 계약을 따른다. OCR의 배경 작은 글씨는 주요 표시 문자와 따로 기록하고, 판독할 수 없는 글자를 추측해서 전사하지 않는다.
